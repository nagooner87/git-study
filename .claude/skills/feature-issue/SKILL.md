# feature-issue

기능을 추가할 때마다 이슈를 수동으로 만들고 라벨을 고르는 일은 번거롭고 자주 빠진다.
이 스킬은 기능 요청이나 작업 흔적에서 이슈 내용을 만들고, 라벨을 맞춘 뒤 바로 등록한다.

**이 스킬은 확인 절차 없이 이슈를 바로 생성한다.** 공개 저장소에 쓰이는 동작이므로, 중복 확인과 제목·라벨 결정을 꼼꼼히 하고 결과 URL은 반드시 보고한다.

## 1. 저장소와 gh 확인

```bash
git remote get-url origin
gh auth status
```

- owner/repo는 `origin` URL에서 읽는다 (`https://github.com/<owner>/<repo>` 또는 `git@github.com:<owner>/<repo>.git`). 값을 하드코딩하지 않는다.
- `gh auth status`가 실패하면 이슈를 만들지 말고 `gh auth login`을 안내한 뒤 끝낸다.
- origin이 GitHub가 아니면 그렇게 알리고 끝낸다.

## 2. 기능 내용 파악

다음 정보를 모은다. 빠진 것은 추측하지 말고 코드와 요청에서 찾는다.

```bash
git branch --show-current
git status --porcelain=v1 -uall
git log --format='%s' -n 10
```

- 사용자 요청: 무엇을 추가하는지 (목적, 기대 동작)
- 브랜치명: `feature/<이름>`이면 기능 이름의 힌트로 쓴다
- 변경 파일: 새로 생긴 `scripts/*.py`, `reports/*.md`, `data/*` 등으로 영역을 본다
- 기능 요청이 너무 모호하면(무엇을 할지 전혀 알 수 없으면) 이슈를 만들지 말고 한 줄로 되묻는다.

## 3. 중복 확인

같은 기능의 이슈가 이미 있으면 새로 만들지 않는다.

```bash
gh issue list --repo <owner>/<repo> --search "<핵심 키워드>" --state all --limit 20
```

- 제목 또는 본문이 거의 같은 기능을 가리키면 생성하지 않고 기존 이슈 번호와 URL을 알린다.
- 애매하면(관련은 있지만 다른 기능일 수 있으면) 생성하고, 관련 이슈 번호를 본문에 `관련: #<번호>`로 적는다.
- 이 저장소에서 이슈 번호는 `#번호`로 쓰지 말고 `<owner>/<repo>#번호` 형식으로 보고한다.

## 4. 제목과 본문 작성

### 제목

`[기능] <요약>` 형식으로 쓴다. 요약은 한글로, 기존 커밋 메시지 스타일(`feat : 승객유형별 하차 분석 추가`)에 맞춘다.
예: `[기능] 승객유형별 하차 분석 추가`

- 50자 안팎, 마침표 없이, "~추가", "~분석" 같은 명사형 종결
- 버그 수정이면 `[버그]`, 문서 작업이면 `[문서]` 머리말을 쓴다

### 본문

임시 파일에 쓴 뒤 `--body-file`로 넘긴다. 스크래치패드 디렉터리를 쓰고, 저장소 안에는 파일을 남기지 않는다.

```markdown
## 배경/목적
<왜 필요한지, 무엇을 해결하는지>

## 구현 내용
- <구현할 항목 1>
- <구현할 항목 2>

## 완료 조건
- [ ] <검증 가능한 조건 1>
- [ ] <검증 가능한 조건 2>

## 관련 파일
- `scripts/<파일>.py`
- `reports/<파일>.md`

관련: #<번호>   <!-- 관련 이슈가 있을 때만 -->
```

- 완료 조건은 실제로 확인할 수 있는 문장으로 쓴다 ("동작한다" 같은 모호한 표현 금지).
- 관련 파일은 실제로 존재하거나 만들 예정인 경로만 적는다.
- 확인하지 않은 사실을 본문에 넣지 않는다.

## 5. 라벨 결정과 생성

### 종류 라벨 (하나 고른다)

| 상황 | 라벨 | 설명 |
|---|---|---|
| 새 기능 | `enhancement` | 기본 라벨 (New feature or request) |
| 버그 수정 | `bug` | 기본 라벨 |
| 문서 작업 | `documentation` | 기본 라벨 |

### 영역 라벨 (있으면 붙인다)

변경 파일 경로로 정한다. 예: `scripts/analysis_*.py`, `reports/analysis_*.md` → `analysis`. 영역이 뚜렷하지 않으면 붙이지 않는다.

### 없는 라벨 생성

```bash
gh label list --repo <owner>/<repo> --limit 100
gh label create "<이름>" --repo <owner>/<repo> --color <6자리 hex, # 없이> --description "<한 줄 설명>"
```

- 먼저 `gh label list`로 확인하고, 이미 있는 라벨은 만들지 않는다.
- 기본 라벨(`enhancement`, `bug`, `documentation` 등)은 있으므로 만들 필요가 없다.
- 영역 라벨은 저장소 색 체계와 겹치지 않게 색을 고른다 (예: `0e8a16`). 설명은 영역이 무엇인지 한 줄로 쓴다.
- 라벨 생성이 실패하면 그 라벨만 빼고 이슈는 만든다. 실패 사유를 결과 보고에 적는다.
- **라벨 삭제, 이름 변경, 색 변경은 하지 않는다.** 기존 라벨을 건드리지 않는다.

## 6. 이슈 생성

```bash
gh issue create --repo <owner>/<repo> --title "<제목>" --body-file "<임시 파일 경로>" --label "<라벨1>,<라벨2>"
```

- 제목과 라벨에 따옴표나 줄바꿈이 들어가지 않게 한다. 본문은 항상 `--body-file`로 넘긴다.
- 실패하면 `gh`가 준 오류 메시지를 그대로 보여주고, 같은 명령을 반복해서 재시도하지 않는다.

## 7. 결과 보고

이슈를 만든 뒤 다음을 짧게 보고한다.

- 이슈 번호와 URL (`https://github.com/<owner>/<repo>/issues/<번호>`)
- 붙인 라벨 목록, 새로 만든 라벨이 있으면 그 목록
- 중복 확인 결과 (관련 이슈가 있었는지)
- 실패한 단계가 있으면 그 사유

## 하지 않는 것

- 이슈 닫기, 수정, 삭제 (사용자가 요청한 경우가 아니면)
- 라벨 삭제, 이름 변경, 색 변경
- 커밋, 브랜치 생성, PR 생성 (이슈 등록만 한다)
- 사용자가 요청하지 않은 이슈를 여러 개 만들기 (기능 하나당 이슈 하나)
